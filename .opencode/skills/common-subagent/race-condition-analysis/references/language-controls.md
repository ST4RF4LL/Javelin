# 按技术栈核查并发控制

只读当前任务涉及的部分；下列机制均须结合实际版本、调用路径与配置判断。锁、事务或关键字的存在/缺失都不是漏洞结论。

| 范围 | 需要核查的事实 |
| --- | --- |
| Java / JVM | `@Transactional` 的真实代理边界、传播/隔离配置、自调用与异步边界；`@Lock` 是否锁到同一行；`@Version` 是否参与写入与冲突处理；`synchronized`/本地锁是否只能保护单实例；外部调用是否在提交前已产生不可回滚的副作用。 |
| Python | Django/SQLAlchemy 的实际事务、连接和锁范围；`select_for_update()` 的数据库支持及生效时机；`F()`/原子更新是否包含业务谓词并检查结果；`asyncio`、线程锁和进程锁保护谁。GIL 不替代跨请求数据库事务，也不覆盖外部存储操作。 |
| Web / JS / TS | 请求在异步 I/O 等位置的交错、服务端多进程/多副本与队列；客户端单线程或按钮禁用不等于服务端原子性。仅见前端时核对可见的协议契约，服务端守卫未知记 GAP。追踪兑换、回调、刷新令牌、余额/配额和任务状态的服务端实现。 |
| C / C++ | 对同一内存对象的冲突访问与 happens-before、mutex/atomic 的作用范围和对象生命周期；不能把原子标记误当整个复合操作原子。文件 TOCTOU 要证明攻击者可修改路径组成/符号链接与检查后替换的窗口；核对实际描述符、`openat`/`fstat` 等绑定，不仅看 API 名字。可见数据竞争还须说明安全影响。 |
| 平台 / 多进程 | 多副本、任务重复投递、分布式锁和租约、过期持有者/fencing、发布审批与制品替换、临时文件与权限切换。仓库配置只能证明声明，部署实例数、队列保证或外部数据库状态未知就保留前提；不运行容器或基础设施命令来“验证”。 |
| AI / Agent | 审批消费与工具执行之间的参数/主体/工具变化、同一审批双重消费、会话或工作区状态混用、预算先查后扣、共享记忆/任务取消与完成的竞争。区分模型输出不确定性与真正共享状态的竞态；保留工具边界专项的已选风险族，不扩大为无关任务。 |

## 存储与副作用

- **数据库：**查看 schema/migration 的实际唯一键、事务隔离配置、SQL 谓词、锁定读与普通读、受影响行数、提交冲突及重试。单行保护不自动保证多行/跨表不变量；未查到隔离配置不能宣称特定后端所有读取都串行。
- **缓存：**区分单命令原子与多命令 read/check/write；核对脚本/事务/CAS 的同一键空间、集群限制、TTL、失败重试和回源数据库行为。
- **外部副作用：**支付、发信、任务执行等不一定随数据库回滚。核对幂等键、事务外盒等实现中的真实唯一键、消费和重试行为，而非仅看到 outbox 命名就排除问题。
- **多资源/多接口：**用资源键和不变量连接操作 A/B。相同根因、相同约束复用证据；取消/完成、审批/修改等不同前提明确保留，禁止无界排列组合。

参考：[PostgreSQL 隔离级别](https://www.postgresql.org/docs/current/transaction-iso.html)、[Django 锁定查询](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update)。部署语义以被测项目实际版本为准。
