# Dynamic validation safety boundaries

- Reports and audit deliverables must be written in Chinese. Machine-readable artifacts (JSON, digests, code comments, identifiers) stay as-is; only human-facing narrative, findings, and report text use Chinese.
- Never reset browser state by killing Chrome or Chromium processes globally. Do not use `pkill`, `killall`, wildcard PID termination, `taskkill`, `Stop-Process`, or equivalent process-wide commands against Chrome. Close only pages or browser contexts created for the current validation through the configured browser controller. If that cannot recover the session, stop and report the blocked state.
- Run dynamic validation only when the user explicitly enables it and supplies an authorized test environment. If the environment switch is disabled or the environment text is empty, record dynamic validation as `SKIPPED` and continue the static workflow without starting an Agent or browser. Otherwise pass the complete text as a private prompt to the dynamic-testing Agent; never require fixed account fields, JSON, or regex matches to admit the prompt. The Agent must understand the supplied target and login information before registering its execution configuration or contacting a target. If necessary information is genuinely absent, it records the specific gap and skips the affected work without asking or pausing the static workflow. For `runtime-testing.v1`, the user determines whether the supplied target is an authorized test environment; do not infer authorization from public/private/loopback IP classification. Validate HTTP(S) URL syntax and restrict requests to the explicitly authorized origins. Legacy quick/manual validation retains its versioned contracts. Never expand to unlisted targets, unrelated tenants, or real-user accounts.
- Do not start dynamic validation merely because a static finding or runtime-validation request exists. A request artifact is only a handoff record and never grants execution permission.
- For XSS, CDP-driven DOM injection may be used only as a quick browser-control probe. It is not application vulnerability evidence. Prefer proving stored XSS submitted through a real application input, surviving refresh or revisit, and executing in a distinct authorized victim account and isolated browser context.
- Use unique, non-destructive proof markers. Do not read or exfiltrate credentials, tokens, personal data, or unrelated records. Never create backdoors, system persistence, or reusable weaponized payloads.
- Attempt to remove stored test payloads through the authorized application cleanup path. Cleanup failure does not erase an otherwise valid finding; record the still-present payload, affected test scope, failed cleanup evidence, and required manual remediation.
- Web 验证使用 Chrome DevTools MCP，不使用或静默回退到 `agent-browser`。动态测试不限定前端、后端或 Web；`runtime-testing.v2` 支持用户明确授权的 SSH 登录与远端命令。仅有 SSH 环境时不得要求 HTTP(S) URL 或启动 Chrome。SSH 主机、端口、身份及操作范围来自完整私有环境原文，凭据不进入公开证据；禁止跳板、隧道及访问未授权目标。命令超时或中断时保留证据并标记远端状态未知，不假定关闭连接等于进程已停止。
- Web validation through Chrome DevTools MCP is cross-platform, including macOS. Do not reject Web testing solely because of the host operating system; check the required tools and their actual availability. Windows-only restrictions belong to Windows desktop control tools such as winapp CLI, not to the Web testing service, Agent, or browser controller.
- Build, deploy, test, and run this platform directly on the host. Do not use or introduce Docker, Podman, Compose, container images, containerized Chrome, or a container-runtime fallback. Docker/Compose files found inside an audited target may still be read as source artifacts, but must not be executed by this platform.
