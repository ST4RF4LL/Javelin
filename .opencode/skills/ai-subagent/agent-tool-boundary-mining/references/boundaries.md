# 工具和框架的静态检查

## TOOL_RCE

追踪调用者或模型输出对命令、参数、解释器输入、动态模块、插件/skill 脚本、MCP stdio 配置的影响。分别识别 shell 字符串解释、可执行文件选择、程序参数二次执行、动态代码编译与受控解释器。`shell:false` 不能排除程序参数或环境触发的执行；存在 exec 也不自动说明有漏洞。

核对完整执行上下文：最终 executable、argv、cwd、PATH、环境变量、装载路径、身份和隔离机制。配置管理权限是否等同于主机执行权限须由项目策略证明。固定可信程序和受控参数、明确授权的管理员执行能力是反例。仅在沙箱内运行代码不能声称宿主逃逸；执行环境不可见时保留 UNKNOWN。

## TOOL_AUTHZ

将可见工具列表与实际调度权限分开。查找 API 直调、function 名称动态索引、skill 的命令/脚本/工具分支、MCP call_tool、批量调用、别名、fallback、重连后更新与子 Agent 委派。统一策略钩子、工具 allowlist、参数/资源限制是否支配每条路径？拒绝是否终止操作？仅告警或只在 UI 隐藏不能当授权。

核对策略检查前后的规范化对象是否相同：tool/server/version/actor/session/target/args/policy。审批如果是必要控制，必须绑定最终执行内容；审批不属于本操作要求时说明依据，不能统一要求额外审批。skill 包内相对路径不等于其根目录已被授权；可信 skill 名称不能替代实际加载源与版本绑定。

## FRAMEWORK_ACCESS

记录原始身份与最终运行身份，验证匿名/公共项目不会落入超级用户或共享服务身份。用户属于 workspace A，不自动拥有 agent/session/run B：必须绑定 B 属于 A。检查 HTTP、WebSocket/SSE、MCP transport、队列恢复、调试/管理路由和后台 job 的共同权限边界。

枚举检查失败、认证方式未知、异常、缓存、配置覆盖和 fallback 分支。不要因没有某个装饰器就断言缺认证；先追踪外层 middleware/依赖注入/网关可证明范围。只能看到远端框架客户端时，远端控制为未知。

## 知识与反证

优先按已见机制检索，而非产品名相同就套用结论。读取根因中的 preconditions、counterexamples、detection_requirements 和 limitations。类型、版本、框架、调用者权限、执行上下文不同需要重新建立证据。库缺失、案例争议或未评估的跨项目泛化，只限制知识支持，不阻止当前源码分析。

负证据要注明完整检查的函数/分支范围和方法，引用覆盖这些分支的源码行段。词法查找未命中不是“控制缺失”的充分证据。调用边必须说明实际数据传递或分派关系，不可仅拼接两个不相关函数。
